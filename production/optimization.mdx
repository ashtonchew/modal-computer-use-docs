Production performance in `modal-computer-use` comes down to one principle: pay startup costs once and minimize work on every subsequent turn. Most measurable latency in a computer-use loop comes from network round trips, screenshot encoding, and unnecessary per-turn overhead — not from the daemon itself. Measure startup and warm-operation latency separately, keep the default configuration until measurements identify a concrete bottleneck, and apply the techniques on this page in order of measured impact.

## Create Once, Keep One Connection

The most important production shape is to create the desktop once and maintain a single connection for the entire agent trajectory. Every turn that re-establishes a connection pays authentication, credential creation, readiness verification, and connection setup costs that belong only on the critical path of session startup.

The [session handoff example](https://github.com/ashtonchew/modal-computer-use/blob/main/examples/modal_function_session_handoff.py) is the canonical production pattern:

<Steps>
  <Step title="Create and own the desktop">
    Your application creates the `ComputerSandbox` and holds the ownership handle.
  </Step>
  <Step title="Pass a session handle to a Modal Function">
    Construct a `ComputerSessionHandle` and pass it to a deployed Modal Function.
  </Step>
  <Step title="Open one borrow context for the full trajectory">
    Inside the Function, open a single `borrow_async()` context around the full observe → model → act loop.
  </Step>
  <Step title="Detach when the trajectory ends">
    The Function detaches on normal return or exception. The handle goes out of scope cleanly.
  </Step>
  <Step title="Terminate from the owner">
    After the Function reaches a terminal result, the application terminates the desktop.
  </Step>
</Steps>

This shape pays startup exactly once. The connection, lease, and daemon state remain available between turns without re-establishing anything. Your application still owns admission, provider calls, deadlines, cancellation, and final cleanup.

```python
# Inside your deployed Modal Function
async def run_trajectory(handle: ComputerSessionHandle) -> str:
    async with handle.borrow_async() as computer:
        while True:
            screenshot = await computer.screenshots.full_bytes_async()
            action = await call_model(screenshot)
            if action.is_terminal:
                return action.result
            await computer.actions.run_async(action.steps)
```

<Note>
  One Function invocation should own the complete repeated loop. Using multiple invocations for a single desktop trajectory adds re-entry overhead and risks concurrent trajectory conflicts — the daemon lease prevents overlapping borrows on the same desktop.
</Note>

## Place the Caller Near the Sandbox

Network round-trip latency between the caller and the Modal sandbox dominates warm-path performance. A co-located runner measured at `1.253ms` transport floor versus `29.911ms` for an external caller in the same broad region — a difference that persists even after daemon action execution is already sub-millisecond.

Pin `modal_region` to the region where your caller or model loop runs:

```python
from modal_computer_use import ComputerConfig, RuntimeConfig

config = ComputerConfig(
    runtime=RuntimeConfig(modal_region="us-west"),
)
```

Run the benchmark from your actual deployment environment to find the fastest region:

```bash
uv run computer-use benchmark modal-region-ab \
  --iterations 30 \
  --modal-region default \
  --modal-region us-west \
  --modal-region us-east \
  --modal-ingress attested-tunnel \
  --caller-region-label my-caller-location \
  --output benchmark-results/region-ab-$(date +%Y%m%d).json
```

Then render the results as a table:

```bash
uv run computer-use benchmark modal-region-summary \
  benchmark-results/region-ab-$(date +%Y%m%d).json
```

| Situation | Policy |
|-----------|--------|
| General SDK usage | Leave `runtime.modal_region` unset — preserves Modal's default availability behavior |
| Production agent loop | Pin to the fastest measured region near your caller/model loop |
| Published latency claim | Run `modal-region-ab` from the actual caller environment |
| Reused sandbox | Region only applies at creation; you cannot relocate an existing sandbox |

Keep brokers, durable stores, and public gateways away from the screenshot and action hot path. They can own admission, recovery, and audit records without relaying every frame.

## Use Async Orchestration

Use `AsyncComputerSandbox` whenever your application already runs on asyncio. In a deployed Modal Function, keep one `borrow_async()` context open for the full trajectory:

```python
from modal_computer_use import AsyncComputerSandbox, ComputerConfig

async def run_agent():
    config = ComputerConfig(runtime=RuntimeConfig(modal_region="us-west"))
    async with AsyncComputerSandbox.create(config) as computer:
        # Full trajectory loop — one connection, one borrow
        while not done:
            frame = await computer.screenshots.full_bytes_async()
            actions = await model.decide(frame)
            await computer.actions.run_async(actions)
```

Native async keeps the event loop free during Modal and daemon I/O. It also provides cancellation-aware cleanup. The `borrow_async()` path runs lease heartbeat renewal on a dedicated private thread so ordinary async work — model calls, screenshots, other desktop tasks — never starves the lease.

<Note>
  Use `asyncio.to_thread()` only as a bridge for blocking I/O from legacy libraries. It does not make CPU-bound or GIL-holding work safe, and it does not make a blocked event loop responsive.
</Note>

## Reduce Per-Turn Work

Each turn in an agent loop should do the minimum work required to make progress. The accumulated cost of unnecessary operations compounds across hundreds of turns.

### Batch Actions

The daemon's `/v1/actions/run` route executes an ordered list of actions under one input lock. Ten individually dispatched actions cost ten HTTP round trips; one batch of ten costs one:

```python
# Instead of dispatching each action separately…
await computer.actions.run_async([
    {"type": "move", "x": 100, "y": 200},
    {"type": "left_click"},
    {"type": "key", "key": "ctrl+a"},
    {"type": "type", "text": "hello"},
])
```

Batch actions when the model returns multiple steps in one turn and none of them require an intermediate screenshot for the model to decide what to do next. The default batch limit is 50 actions (configurable via `COMPUTER_USE_MAX_BATCH_ACTIONS`). Pass `continue_on_error=True` when a flaky action should not abort the rest.

```bash
# Measure batching impact on your deployment
uv run computer-use benchmark action-batch \
  --base-url "$COMPUTER_USE_DAEMON_URL" \
  --token "$COMPUTER_USE_TOKEN" \
  --iterations 10
```

### Use Binary Screenshot Routes

Avoid the JSON/base64 screenshot path on the hot path. Use the binary routes instead:

```python
# Fastest: fused action + screenshot in one request
screenshot_bytes = await computer.actions.run_and_screenshot_bytes_async(actions)

# Fast: binary screenshot only
screenshot_bytes = await computer.screenshots.full_bytes_async()
```

For tight loops that require change detection, use the observation stream:

```python
async with computer.observation_stream(fps=0.01) as stream:
    frames = stream.frames()
    first = await anext(frames)
    await stream.run_actions_capture_async(
        actions=[{"type": "left_click", "x": 100, "y": 200}]
    )
    observed = await anext(frames)
```

### Fused Action-and-Screenshot Requests

When the immediate post-action frame is your required observation, use `run_and_screenshot_bytes` instead of a separate action call followed by a screenshot call. This eliminates one full network round trip per turn:

```python
# One request: run actions AND get the screenshot back
screenshot = await computer.actions.run_and_screenshot_bytes_async([
    {"type": "left_click", "x": 400, "y": 300},
])
# Pass screenshot directly to your model
```

## Enable HTTP/2 for Connection Reuse

For hot primitive loops that issue many requests per second, enable HTTP/2 via `network.daemon_http_version`:

```python
from modal_computer_use import ComputerConfig, NetworkConfig

config = ComputerConfig(
    network=NetworkConfig(daemon_http_version="2"),
)
```

This exposes the daemon port through Modal `h2_ports`, starts the daemon under Hypercorn, and uses an `httpx` HTTP/2 client. HTTP/2 multiplexes multiple requests over one connection, reducing connection overhead for bursty action loops. HTTP/1.1 remains the SDK default for broadest compatibility; switch to HTTP/2 only after benchmarking confirms a benefit on your workload.

## Understand Receipt Durability Cost

Each leased mutation crosses one SQLite WAL commit with `synchronous=FULL` before the daemon dispatches the mutation. This is a surviving-target-filesystem guarantee — it ensures that no mutation is dispatched without a surviving `IN_PROGRESS` receipt — but it adds a small per-action cost on every write path.

This cost is paid only at the safety boundary. Terminal receipt bookkeeping uses the weaker `synchronous=NORMAL`. You cannot eliminate the `FULL` sync without removing the safety guarantee. If per-action latency is dominated by this cost in your environment, measure it with alternating `FULL` and `NORMAL` pre-dispatch transactions on the same filesystem before drawing conclusions — and never move the SQLite WAL to a Modal Volume or a network filesystem.

## Warm Capacity

For time-sensitive workloads where cold-start latency is unacceptable, pre-provision desktops with a warm pool. See the [Warm Pool guide](/production/warm-pool) for the full pattern.

At a high level:

- **Function warm capacity** reduces the wait for a deployed Function container to be available.
- **Desktop warm pools** reduce the wait for a ready sandbox with a running desktop.

Both add idle cost. Measure pool hit rate, cold fallback rate, remaining lifetime, and cost before increasing capacity.

## Put Dependencies in the Image

Stable system and Python dependencies belong in the Modal Image, not in startup scripts that run at sandbox creation time. Structure your image layers so frequently changed application files are in later layers — Modal can reuse earlier layers from cache:

```python
import modal

# Stable dependencies in base layers
base_image = (
    modal.Image.debian_slim()
    .pip_install("requests", "pillow")
    # Frequently changed app code in the last layer
    .copy_local_file("app.py", "/app/app.py")
)
```

Browser prewarm (`BrowserConfig(prewarm=True)`) reduces first-page latency after sandbox startup. Enable it after you've confirmed browser startup appears in your measured performance boundary.

## Measure the Complete Boundary

Record measurements with enough context to reproduce them:

- Caller location and topology (external vs. co-located, region)
- Requested and observed Modal placement
- Ingress type, image revision, resources, and browser setup
- Whether the sandbox was cold or warm, and the exact timer boundary
- Sample count, p50, p95, failures, and cost

Use at least 30 measured samples when reporting p95. Keep raw samples. Daemon-only timing omits transport, authentication, and response processing — always record caller-observed elapsed time.
