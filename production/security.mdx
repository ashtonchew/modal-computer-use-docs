The daemon has full desktop control. It can click, type, read the clipboard, launch applications, and read or write artifacts on any surface exposed to it. This means that tokens, session URLs, and VNC access URLs carry the same risk as API keys or SSH credentials — they grant unrestricted interactive access to a running desktop. This page explains the authentication modes you use as a customer, how to handle tokens safely, how to configure noVNC access, and what the SDK already does to protect sensitive data in structured logs.

## Authentication Modes

`modal-computer-use` supports three authentication modes depending on your deployment context.

### Modal Connect Ingress (Default for Most Users)

When you create a sandbox with `ingress="connect"` (the default for many configurations), all daemon requests travel through Modal's Connect infrastructure. Modal forwards verified user metadata in the `X-Verified-User-Data` header, and the SDK trusts that header only for this ingress mode. Each request carries Modal verified-user identity automatically.

### Attested Tunnel (SDK Default)

The SDK default is `ingress="attested-tunnel"`. This mode bootstraps through a Modal Connect Token to mint a short-lived session token, then routes hot primitive calls through an encrypted Modal tunnel on port `8080`. This is the recommended mode for production use: it keeps Modal Connect as the authorization bootstrap while reducing per-request overhead after the session is established.

```python
from modal_computer_use import ComputerConfig

# Attested tunnel is the default — no explicit configuration needed
config = ComputerConfig()

# Or set it explicitly:
config = ComputerConfig(ingress="attested-tunnel")
```

Minted session tokens have a **one-hour default lifetime** and an unlimited active-session count by default. Operators can configure a positive lifetime and an optional active session cap. Expired tokens are pruned on access. A full configured token store rejects minting instead of evicting active clients.

### Local Development

For local testing only, set `COMPUTER_USE_LOCAL_TOKEN` in the daemon's environment and have clients send `Authorization: Bearer <token>`:

```bash
export COMPUTER_USE_LOCAL_TOKEN=my-local-dev-token
```

<Warning>
  `COMPUTER_USE_LOCAL_TOKEN` is for local testing only. Never set a weak token in a production deployment, and never expose port `8080` to untrusted networks with a weak or missing token. The daemon fails closed when no authenticator is configured; `COMPUTER_USE_ALLOW_UNAUTHENTICATED_LOOPBACK=true` is a local development flag only.
</Warning>

## Token Handling

Tokens and session URLs are secrets. Treat them with the same discipline you apply to database passwords or API keys.

<Warning>
  **Never** log bearer tokens, include them in shared shell history, commit them to source control, or paste them into chat or ticketing systems. The SDK strips tokens from benchmark report outputs and log-safe metadata, but your own code must not forward them.
</Warning>

### Why Query-String Tokens Are Rejected

By default, `COMPUTER_USE_REJECT_QUERY_TOKENS=true`. Tokens passed in URL query strings are rejected because URLs appear in proxy logs, browser history, server access logs, and error messages. Passing a token as a query parameter in any environment with logging enabled will likely leak it. Keep this default unless you have a specific, understood reason to disable it:

```bash
# Only disable if you fully understand the leakage risk
COMPUTER_USE_REJECT_QUERY_TOKENS=false
```

### Desktop Child Processes Cannot Inherit Tokens

Desktop child processes do not inherit daemon-owned token or password variables. A minted token cannot directly call process execution routes or mint another token. This limits the blast radius if code running on the desktop is compromised: it cannot escalate to daemon credentials.

### Subprocess Argument Safety for Typed Text

When typing text via the compatibility path (`method="xdotool"`), text is passed to `xdotool type --file -` through subprocess stdin rather than as a command-line argument. This prevents typed text from appearing in process listings or `/proc/<pid>/cmdline` inspection. The plaintext still exists in daemon memory and the stdin pipe while the action runs — this is exposure reduction, not encryption.

## noVNC Access

noVNC provides a browser-based view of the live desktop. The `expose_vnc` option controls whether the VNC server runs and what level of access it grants.

<Accordion title="expose_vnc='off' (Default)">
  No VNC server runs. This is the secure default. Use it for all production deployments where human observation is not required.

  ```python
  from modal_computer_use import ComputerConfig
  # expose_vnc defaults to "off" — no additional configuration needed
  config = ComputerConfig()
  ```
</Accordion>

<Accordion title="expose_vnc='view_only'">
  A noVNC tunnel is created that lets viewers watch the desktop in real time but not click or type. The daemon starts `x11vnc` with a password file. The SDK generates a per-sandbox VNC password automatically and does not include it in metadata, tags, URLs, or logs.

  ```python
  config = ComputerConfig(expose_vnc="view_only")
  ```

  The noVNC URL is a secret. Treat it like a bearer token: never share it in chat, tickets, or shared logs.
</Accordion>

<Accordion title="expose_vnc='control'">
  A noVNC tunnel is created with full remote input — viewers can click and type on the desktop.

  ```python
  config = ComputerConfig(expose_vnc="control")
  ```

  <Warning>
    `expose_vnc="control"` grants full interactive desktop access to anyone who has the noVNC URL and password. Never expose a control-mode noVNC URL to the public internet or share it in any unsecured channel. If you need operator-controlled access, provide `COMPUTER_USE_VNC_PASSWORD` through your own secret channel and still treat both the URL and password as secrets.
  </Warning>
</Accordion>

### If a noVNC URL Is Accidentally Shared

Treat the URL as compromised. Terminate the sandbox immediately. The next sandbox you create with `expose_vnc` enabled will receive a fresh tunnel and a freshly generated VNC password:

```python
# Terminate the compromised sandbox
await computer.terminate()

# Create a fresh sandbox — new VNC URL and password
config = ComputerConfig(expose_vnc="view_only")
new_computer = await AsyncComputerSandbox.create(config)
```

## Log Redaction

The daemon's structured logs automatically redact sensitive data. You do not need to configure this, but you should understand what is protected:

| Data type | Log treatment |
|-----------|--------------|
| Typed text | Redacted — logged as `{"redacted": true, "length": N}` |
| Clipboard text | Redacted |
| Screenshot bytes | Redacted |
| Bearer tokens | Redacted |
| Provider API keys | Redacted |
| noVNC URLs | Redacted |
| Artifact bytes | Redacted |
| Action types, elapsed time, `call_id` | Retained |
| Image dimensions | Retained |

Content hashes are not retained for redacted values. This means you cannot correlate redacted log entries back to their content even with the original data.

OpenTelemetry tracing is disabled by default. When you enable it with `COMPUTER_USE_OTEL_ENABLED=true`, spans use route paths and bounded action/artifact metadata — they do not include query strings, `Authorization` headers, typed text, clipboard text, screenshot bytes, recording bytes, stdout, or stderr.

### Action Traces

Trace validation treats raw plaintext in `type` actions as unsafe. New action traces use `redactions=["text"]` and replace typed text with redaction metadata before writing NDJSON. Replay dry-runs skip redacted typed text because the original plaintext is intentionally absent.

## Authenticated Debug Routes

Debug routes that intentionally return command output or process log tails sanitize known secret-bearing substrings — bearer tokens, noVNC URLs, and artifact URIs — before sending the response. These routes require authentication and are not unauthenticated diagnostic endpoints.

## Provider Credentials

The daemon image does not include OpenAI or Anthropic credentials, and the daemon does not require them. Provider SDK calls belong in your application code, not in the daemon image.

Treat screen content, typed text, clipboard text, and provider-returned tool payloads as untrusted input. Provider fixtures should contain only synthetic actions — no credentials, tokens, screenshots, clipboard contents, or user data.

## Modal Resource Ownership

New Modal sandboxes carry a `computer-use.app_id` ownership tag. All listing, name lookup, ID attach, reuse, and cleanup operations are scoped to the requested Modal app and verify that tag. Broad cleanup operations never terminate an untagged sandbox automatically.

## Reporting Security Issues

If you discover a security vulnerability, please report it through the project's security disclosure process. Do not open a public GitHub issue for security vulnerabilities.
