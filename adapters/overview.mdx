Provider adapters are the bridge between AI model output and your desktop sandbox. When OpenAI's Responses API or Anthropic's Messages API returns a computer-use action, the adapter translates that provider-specific JSON payload into the native `modal-computer-use` action schema and dispatches it to the running daemon. Adapters do **not** call any provider API — they are pure translation and execution layers that sit between your model loop and the desktop.

## How adapters work

Every adapter follows the same pipeline:

1. **Receive** provider-returned action JSON (e.g., an OpenAI `computer_call` or an Anthropic `tool_use` block).
2. **Validate** the action against the provider's known action set.
3. **Normalize** the provider fields to the native `ComputerAction` schema.
4. **Transform** coordinates if you supplied a `CoordinateSpace`.
5. **Check** the `before_action` policy hook (if provided).
6. **Dispatch** the validated, normalized action to `computer.actions`.

<Note>
Adapters never hold prompts, manage conversation history, or call provider SDKs. Your application code owns the model loop, message history, and turn limits.
</Note>

## Installation

Install the extras for the provider you need. You can install both at once if your application supports multiple providers.

<CodeGroup>
```bash OpenAI
uv add "modal-computer-use[openai]"
```

```bash Anthropic
uv add "modal-computer-use[anthropic]"
```

```bash Both + Modal
uv add "modal-computer-use[modal,openai,anthropic]"
```
</CodeGroup>

<Tip>
The `modal` extra is required when you run desktops on Modal infrastructure. The provider extras (`openai`, `anthropic`) install only the output helpers — the adapters themselves do not depend on the provider SDKs at runtime.
</Tip>

## Coordinate spaces

Your model reasons from the screenshot you sent it. If that screenshot is a different size from the actual desktop resolution — for example, you downscaled a 1440×900 desktop to 720×450 before sending it to the model — you need to tell the adapter about this difference. Without a `CoordinateSpace`, the adapter passes model coordinates straight to the daemon, which would place clicks and moves at the wrong position.

Pass a `CoordinateSpace` at adapter construction time:

```python
from modal_computer_use import CoordinateSpace
from modal_computer_use.adapters.openai import OpenAIAdapter

space = CoordinateSpace(
    desktop_width=1440,
    desktop_height=900,
    image_width=720,
    image_height=450,
)
adapter = OpenAIAdapter(computer, coordinate_space=space)
```

The adapter multiplies every model coordinate by the ratio `(desktop / image)` before sending it to the daemon. When you do not supply a `CoordinateSpace`, the adapter leaves coordinates unchanged.

The same parameter is available on `AnthropicAdapter` and `ActionExecutor`.

## Policy hooks

A `before_action` hook lets you intercept every normalized action before the daemon executes it. The hook receives the `ComputerAction` (already coordinate-transformed) and a context dict, and returns an `ActionDecision`.

```python
from modal_computer_use.models import ActionDecision
from modal_computer_use.adapters.openai import OpenAIAdapter

def my_policy(action, context):
    # Deny right-clicks; ask for confirmation before typing
    if action.type == "type":
        return ActionDecision(decision="ask_user", reason="typing requires confirmation")
    if action.type == "click" and action.button != "left":
        return ActionDecision(decision="deny", reason="only left clicks are allowed")
    return ActionDecision(decision="allow")

adapter = OpenAIAdapter(computer, before_action=my_policy)
```

If the hook returns anything other than `ActionDecision(decision="allow")`, the executor raises `UnsupportedActionError` before any action reaches the daemon.

### `ActionDecision` values

| `decision` | Effect |
|---|---|
| `"allow"` | Execute the action normally. |
| `"deny"` | Raise `UnsupportedActionError` immediately. |
| `"ask_user"` | Raise `UnsupportedActionError` with the provided `reason`. Your loop should surface the reason to the user. |
| `"handoff"` | Raise `UnsupportedActionError`. Use when the action should be delegated to a human operator rather than denied silently. |

For **atomic response-level preflight** — where you want to check every action in a response before dispatching any of them — call the hook over every normalized action tree before dispatching the first call. The OpenAI loop example demonstrates this pattern.

## `allow_unknown` — compatibility escape hatch

By default, an action type that the adapter does not recognize raises `UnsupportedActionError`. This protects you from silently executing unintended actions when a provider adds new action types in the future.

Set `allow_unknown=True` only when you specifically need to accept unknown provider actions without breaking the loop:

```python
adapter = OpenAIAdapter(computer, allow_unknown=True)
```

In this mode, the adapter converts the unknown action to a zero-duration `wait` and stores redacted provider metadata on the action. **The unknown action is never executed on the desktop.** The native `ActionExecutor` still rejects unknown `ComputerAction` types; only the provider normalization step is relaxed.

<Warning>
`allow_unknown=True` is a forward-compatibility escape hatch. Do not rely on it for actions you expect to execute. Audit uses carefully.
</Warning>

## Provider-shaped output helpers

After you execute an action, you need to return a screenshot to the model in the format the provider expects. These pure helper functions convert a native `Screenshot` (or `ActionResult`) to the correct provider payload — without calling any provider API or importing provider SDKs.

### OpenAI

```python
from modal_computer_use.adapters.openai import (
    openai_computer_call_output,
    openai_screenshot_metadata,
)

# Build the computer_call_output input item for the next Responses API call
output_item = openai_computer_call_output(
    post_batch_screenshot,
    call_id="call_abc123",
)

# Record safe metadata (no image bytes or base64) for tracing
metadata = openai_screenshot_metadata(post_batch_screenshot)
```

### Anthropic

```python
from modal_computer_use.adapters.anthropic import (
    anthropic_tool_result,
    anthropic_screenshot_content,
    anthropic_screenshot_metadata,
)

# Build the tool_result content block for the next Messages API call
tool_result = anthropic_tool_result(
    tool_use_id="toolu_xyz",
    result=screenshot,
)

# Build a bare image content block (for multi-part tool results, e.g. computer_batch)
image_block = anthropic_screenshot_content(screenshot)

# Record safe metadata (no image bytes or base64) for tracing
metadata = anthropic_screenshot_metadata(screenshot)
```

`openai_screenshot_metadata()` and `anthropic_screenshot_metadata()` both return a dict containing dimensions, format, SHA-256, artifact URI, capture time, and coordinate space — but **never** raw image bytes or base64 data.

## Tracing and sensitive data

Adapters never write sensitive data to traces. Typed text and other sensitive provider fields are automatically redacted before they reach any trace output. The normalized native action (what actually executed on the desktop) is recorded separately from the original provider action. This means your trace logs are safe to store and review without risk of leaking passwords, typed text, or other sensitive input.
