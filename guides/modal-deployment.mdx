`modal-computer-use` runs a Linux desktop inside a Modal Sandbox and manages the full lifecycle — from image selection and resource allocation through ingress, tagging, persistent storage, and eventual cleanup. This guide walks you through every major deployment decision so you can build reliable, reproducible desktop automation on Modal.

## Image selection

When you call `ComputerSandbox.create()`, the SDK selects a container image based on `ImageConfig.source`:

<Tabs>
  <Tab title="Inline (default)">
    The **inline** source builds or selects the SDK's own managed recipe at runtime. This is the default and the safe rollback path when a named image is unavailable.

    ```python
    from modal_computer_use import ComputerConfig, ImageConfig

    config = ComputerConfig(
        image=ImageConfig(source="inline"),  # this is the default; can be omitted
    )
    ```
  </Tab>
  <Tab title="Named (pinned revision)">
    The **named** source pulls a revision-tagged standard, Firefox, or Chromium image that was published with `scripts/publish_modal_images.py`. You must supply a full 40-character Git SHA as the revision. Modal image tags are treated as write-once by repository policy, so a SHA pin reliably identifies the same image.

    ```python
    from modal_computer_use import ComputerConfig, ImageConfig

    config = ComputerConfig(
        image=ImageConfig(
            source="named",
            revision="a3f1c2e4b8d0e9f6a1b2c3d4e5f6a7b8c9d0e1f2",  # full 40-char Git SHA
        ),
    )
    ```

    Named images require XFCE as the window manager and need an explicit `browser.kind` plus `browser.prewarm=True` for the `browser` and `browser-gpu` profiles.
  </Tab>
</Tabs>

## Resource profiles

`ResourceConfig.profile` selects the managed image recipe and informs the daemon's capability reporting:

| Profile | When to use |
|---|---|
| `standard` | General desktop automation without a persistent browser. |
| `browser` | Browser-heavy workloads. Pairs with `BrowserConfig`. |
| `browser-gpu` | Browser workloads where GPU-accelerated rendering is the bottleneck. Requires an explicit `gpu` value. |
| `custom` | Pass your own `image=` to `ComputerSandbox.create()`. Not supported for named images. |

```python
from modal_computer_use import (
    BrowserConfig,
    ComputerConfig,
    ComputerSandbox,
    ResourceConfig,
)

config = ComputerConfig(
    resources=ResourceConfig(
        profile="browser",
        cpu=4,
        memory_mib=8192,
    ),
    browser=BrowserConfig(kind="chromium", prewarm=True),
)

with ComputerSandbox.create(config=config) as computer:
    computer.browser.open_url("https://example.com")
```

<Note>
`resources.cpu` and `resources.memory_mib` are requests, not caps. Modal charges whichever is higher — the request or actual usage — so avoid over-provisioning if you are cost-sensitive.
</Note>

## Ingress options

The `ingress` field on `ComputerConfig` controls how the SDK reaches the in-Sandbox daemon. There are three choices:

<Accordion title="attested-tunnel (default)">
The SDK manages a bootstrap bearer token that mints a short-lived session token for low-latency tunnel calls on port `8080`. This is the recommended default for most production workloads because it minimises round-trip latency while still using an authenticated, encrypted path.

```python
config = ComputerConfig(ingress="attested-tunnel")  # default; can be omitted
```
</Accordion>

<Accordion title="connect">
All daemon traffic stays on Modal Connect. Use this when you want to rely entirely on Modal's own authenticated HTTP/WebSocket ingress — for example, when you are blocking all outbound network from the Sandbox (`network.block_all=True`) or in environments where outbound tunnel establishment is restricted.

```python
config = ComputerConfig(ingress="connect")
```
</Accordion>

<Accordion title="tunnel">
Uses the bootstrap bearer token directly without the short-lived session exchange. This avoids the attestation round-trip, making it useful for trusted benchmark harnesses where you want the lowest possible overhead and do not need session rotation.

```python
config = ComputerConfig(ingress="tunnel")
```
</Accordion>

## Region placement

Pin the Sandbox to a Modal region by setting `modal_region` inside the `runtime` dict (or a `RuntimeConfig` object):

```python
from modal_computer_use import ComputerConfig

config = ComputerConfig(
    runtime={"modal_region": "us-west"},
)
```

<Tip>
Leave `modal_region` unset during development and only pin it after measuring latency from your actual caller environment. The region string you pass is a scheduling policy selector (e.g. `"us-west"`), not an exact data-center address. Broad selectors preserve scheduling flexibility; narrow ones can reduce availability and increase cost.
</Tip>

Region is baked into the config hash, so `attach_or_create()` will not silently reuse a Sandbox that was created for a different requested region. Attach and recovery operations cannot move a running Sandbox to a new region — you must create a fresh Sandbox with the new config.

## VNC exposure

The `expose_vnc` field controls whether noVNC is exposed and in what mode:

| Value | Behaviour |
|---|---|
| `"off"` (default) | noVNC is disabled. No port `6080` is exposed. |
| `"view_only"` | noVNC port `6080` is exposed. Viewers can watch but cannot send input. |
| `"control"` | noVNC port `6080` is exposed. Viewers can send keyboard and mouse input. |

```python
config = ComputerConfig(expose_vnc="view_only")
```

<Warning>
Never expose noVNC to the public internet without an access-controlled tunnel in front of it. The daemon controls the desktop and can access clipboard contents, screenshots, recordings, and artifacts. `"control"` mode additionally allows remote input. Use noVNC only through a secure, authenticated tunnel during development or debugging.
</Warning>

Use `ComputerSandbox.debug_urls()` (not the daemon-only `computer.debug.urls()`) when you need to retrieve a Modal noVNC URL.

## Tags and run_id

Every Sandbox created by the SDK receives a set of built-in tags for identification and recovery:

| Tag | Purpose |
|---|---|
| `computer-use.run_id` | Your correlation identifier, set from `ComputerConfig.run_id`. Auto-generated if not provided. |
| `computer-use.owner` | The owner label for multi-Sandbox environments. |
| `computer-use.created_at` | ISO-8601 creation timestamp used by cleanup. |
| `computer-use.config_hash` | Validates config compatibility on attach. |
| `computer-use.artifacts_dir` | Records the artifact root path. |

```python
config = ComputerConfig(run_id="support-ticket-42")
```

You can attach later using the same `run_id`:

```python
with ComputerSandbox.attach(run_id="support-ticket-42") as computer:
    screenshot = computer.screenshots.full()
```

Modal's Sandbox tag limit is 10 per Sandbox. The SDK validates the resolved tag set against that limit before allocation.

## Attach and recovery

Use `ComputerSandbox.attach()` to connect to an existing Sandbox by any of four selectors:

```python
# By Modal Sandbox ID
ComputerSandbox.attach(sandbox_id="sb-...")

# By app-scoped name
ComputerSandbox.attach(name="support-desktop", app_name="modal-computer-use")

# By run_id tag
ComputerSandbox.attach(run_id="support-ticket-42")

# By direct daemon URL (no Modal Sandbox resolved)
ComputerSandbox.attach(base_url="https://daemon.example", token="secret-token")
```

Pass exactly one selector. Attaching does **not** transfer lifecycle ownership — leaving an attached `with` block closes the SDK connection but keeps the Sandbox running. Only `create()` owns the Sandbox lifecycle.

`attach_or_create(name=...)` acquires a live named Sandbox or creates one if it is missing:

```python
with ComputerSandbox.attach_or_create(
    name="support-desktop",
    config=ComputerConfig(),
) as computer:
    computer.browser.open_url("https://example.com")
```

If two callers race to create the same named Sandbox, the loser performs a bounded lookup of the winner instead of allocating a duplicate.

## Cleanup

`ComputerSandboxManager.cleanup_expired()` scans Modal Sandbox tags and terminates Sandboxes older than a configurable TTL:

<Steps>
  <Step title="Dry run first">
    The default is `dry_run=True`, which returns a `SandboxCleanupResult` describing what *would* be terminated without actually stopping anything.

    ```python
    from modal_computer_use import ComputerSandboxManager

    result = ComputerSandboxManager.cleanup_expired(
        ttl_seconds=3600,
        dry_run=True,
    )
    print(result.candidates)  # Sandboxes that would be terminated
    print(result.skipped)     # Sandboxes skipped due to missing metadata
    ```
  </Step>
  <Step title="Apply cleanup">
    Pass `dry_run=False` to actually terminate the expired Sandboxes. Only Sandboxes with a valid `computer-use.created_at` tag older than the TTL cutoff are terminated. Sandboxes with missing or malformed creation metadata are always skipped.

    ```python
    result = ComputerSandboxManager.cleanup_expired(
        ttl_seconds=3600,
        owner="my-app",   # optional: scope to one owner label
        dry_run=False,
    )
    print(f"Terminated {len(result.candidates)} sandboxes")
    ```
  </Step>
</Steps>

## Persistent storage with Modal Volume v2

By default, artifacts live only in the Sandbox filesystem and are lost when the Sandbox terminates. To persist artifacts across sessions, mount a Modal Volume v2 at the artifact directory and enable `persist_artifacts`:

<Steps>
  <Step title="Create or reference a Volume">
    ```python
    import modal
    from modal_proto import api_pb2

    volume = modal.Volume.from_name(
        "my-computer-use-artifacts",
        create_if_missing=True,
        version=api_pb2.VolumeFsVersion.Value("VOLUME_FS_VERSION_V2"),
    )
    volume = volume.hydrate()
    ```
  </Step>
  <Step title="Create the Sandbox with the Volume mounted">
    Pass the Volume in the `volumes` dict and set `persist_artifacts=True` in `StorageConfig`:

    ```python
    from modal_computer_use import ComputerConfig, ComputerSandbox, StorageConfig

    ARTIFACTS_DIR = "/home/desktop/artifacts"

    config = ComputerConfig(
        storage=StorageConfig(persist_artifacts=True),
    )

    computer = ComputerSandbox.create(
        config=config,
        volumes={ARTIFACTS_DIR: volume},
    )
    ```
  </Step>
  <Step title="Write artifacts and sync">
    After writing artifacts, call `sync()` to commit them to the Volume. The method returns an `ArtifactSyncResult`; check both `ok` and `persistent` before proceeding.

    ```python
    computer.wait_until_ready()

    computer.artifacts.write_bytes("runs/my-run/result.txt", b"done\n", "text/plain")

    sync = computer.artifacts.sync()
    if not sync.ok or not sync.persistent:
        raise RuntimeError("Volume sync did not succeed")
    ```
  </Step>
  <Step title="Reload the Volume in other readers">
    Other processes that already have the Volume mounted must call `reload_volumes()` before they can see the newly committed files:

    ```python
    computer.reload_volumes(timeout=55)
    ```
  </Step>
</Steps>

<Note>
Modal Volume v1 is not a supported immediate-sync target. Always use Volume v2 (`VOLUME_FS_VERSION_V2`). `modal.NetworkFileSystem` is intentionally unused by the SDK.
</Note>

The full working example is [`examples/volume_artifacts.py`](https://github.com/ashtonchew/modal-computer-use/blob/main/examples/volume_artifacts.py). It accepts `--volume-name` (or the `MODAL_COMPUTER_USE_VOLUME_NAME` environment variable) and an optional `--create-volume` flag:

```bash
uv run python examples/volume_artifacts.py --volume-name computer-use-artifacts
uv run python examples/volume_artifacts.py --volume-name computer-use-artifacts --create-volume
```
